## 3. Architecture

Monolithic server-rendered Laravel MVC app (single deployable, no microservices, no monorepo). Layering:

```
Browser (Blade + jQuery + Bootstrap5 + DataTables via CDN/public assets)
        │  HTTP (session auth, CSRF token)
        ▼
routes/web.php  ──────────────►  Controllers (app/Http/Controllers)
                                        │  (validates via Form Requests)
                                        ▼
                                  Services (app/Services) ── extends BaseService
                                        │  (DB transactions, fires Events)
                                        ▼
                                  Models (app/Models, Eloquent + Traits)
                                        │
                                        ▼
                                     MySQL
                                        
                    Events (app/Events/<Domain>/*) ──► Listeners (app/Listeners/<Domain>EventListener)
                    DataTables (app/DataTables/<Domain>DataTable) ── server-side AJAX for index/trash tables
```

- **Controller → Request (validation) → Service (business logic + DB transaction + event dispatch) → Model** is the enforced pattern for every CRUD domain (see Brand as reference: [app/Http/Controllers/BrandsController.php](app/Http/Controllers/BrandsController.php), [app/Http/Requests/Brand/StoreBrandRequest.php](app/Http/Requests/Brand/StoreBrandRequest.php), [app/Services/BrandService.php](app/Services/BrandService.php)).
- Controllers do **not** talk to Eloquent directly for writes — only Services do. Reads for list pages go through DataTables classes, which query the model directly.
- Events per domain (Created/Updated/Deleted/Destroyed/Restored, plus domain-specific ones like `BrandStatusUpdated`) are dispatched from the Service layer. Listeners exist as one class per domain implementing Laravel's **event subscriber** pattern (`subscribe()` method) but their handler methods are empty stubs — hook point for future side effects (notifications, cache busting, etc.).
- **Laravel 12 auto-discovers events/listeners** (`->withEvents(discover: true)` in [bootstrap/app.php:20](bootstrap/app.php#L20)) — per user instruction, **do not manually register listeners** in a ServiceProvider; new domain events/listeners just need to follow the existing naming convention to be picked up.
- No API layer active yet (`routes/api.php` is empty; `laravel/passport` installed but unconfigured) — planned for later.

## 7. Conventions & Patterns

- **Route naming**: flat, non-prefixed names — `brand.index`, `role.index`, `user.assign-roles`, etc. **Never** `admin.role.index` style (explicit project rule).
- **Route structure per domain** (see `brand`, `role`, `user`, `permission`, `division`, `district`, `thana`, `faq` in [routes/web.php](routes/web.php)): `index`, `create`, `store`, `trash`, then a `{model}`-scoped subgroup: `show` (with `->withTrashed()`), `edit`, `update` (PATCH), `destroy` (soft-delete, DELETE), `restore` (POST), `delete` (force-delete, DELETE `force-delete`). Domain-specific extras hang off the same subgroup (e.g. brand's `update-status`, role's `edit-permissions`/`update-permissions`, user's `assign-roles`/`assign-permissions`/`change-password`/`activities`/`login-history`).
- **Controller pattern**: constructor-injected Service; every write action wrapped in try/catch distinguishing `GeneralException` (expected, message shown to user) vs generic `Throwable` (logged, generic message shown). Destructive/status/restore actions return `JsonResponse` (called via AJAX); create/update return `RedirectResponse` with flash `success`/`error`.
- **Service pattern**: every mutating method wraps `DB::beginTransaction()/commit()/rollBack()`, fires a domain Event on success, throws `GeneralException` with a user-facing message on failure (original exception logged via `Log::alert`/`Log::error`). Soft-delete ("destroy") sets `deleted_by` and `is_active=false` via `activity()->withoutLogs()` before calling `->delete()` (avoids a spurious "updated" activity-log entry alongside the "deleted" one). Restore reverses this. Force-delete additionally logs an explicit `forceDeleted` activity entry (since `forceDelete()` doesn't emit its own).
- **Form Requests**: one `Store*Request`/`Update*Request` pair per domain, `authorize()` always returns `true` (authorization is not yet enforced at the Request/Policy level — see Open Questions), `rules()` + a matching `messages()` array with per-rule custom text.
- **Activity logging convention**: `LogsActivity` trait + `getActivitylogOptions()` per model; `Brand` uses `useLogName('brand')->logAll()->logOnlyDirty()`. Status-only updates use `saveQuietly()` to suppress the automatic "updated" log, then manually log a custom named event (`statusUpdated`) via the `activity()` helper — replicate this exact pattern for any other "special update that isn't a full edit" action.
- **Soft-delete / Trash / Restore / Hard-delete**: every core domain model uses `SoftDeletes` + an explicit `deleted_by` column (not just `deleted_at`). Controllers expose 3 destructive endpoints: `destroy` (soft), `restore`, `delete` (force). DataTables toggle between active/trashed views via a public `showTrashed` property set by the controller before `render()`.
- **DataTables pattern**: one class per domain extending `Yajra\DataTables\Services\DataTable`; `query()` branches on `showTrashed` (`onlyTrashed()` vs `withoutTrashed()`); `dataTable()` defines column transforms (badges via raw HTML + `rawColumns()`); `actions` column renders a separate `<domain>/actions.blade.php` or `actions_trashed.blade.php` partial (view-based row actions, not raw HTML strings) — action buttons trigger AJAX (jQuery `$.ajax`) with SweetAlert2 confir…then Toastify for feedback, using `sessionStorage` to persist the toast message across the redirect after an AJAX action.
- **Blade view structure per domain**: `index.blade.php` (DataTable list + create/trash links), `create.blade.php`, `edit.blade.php`, `show.blade.php` (detail/modal-style view), `trashed.blade.php` (trash box list), `actions.blade.php` + `actions_trashed.blade.php` (row action partials rendered from the DataTable class, not included via `@include` in the main view).
- **Naming**: PascalCase classes, camelCase methods, snake_case DB columns/routes segments — standard Laravel convention, no deviation found.
- **Error/exception handling**: custom `App\Exceptions\GeneralException` is the "expected error, safe to surface to user" signal, thrown from Services; Controllers catch it before falling back to a generic `Throwable` catch.
- **Linting/formatting**: `laravel/pint` is installed (`composer.json` require-dev) but **no `pint.json` config file exists** — it will run with Laravel's default preset. No `.php-cs-fixer` config found. No ESLint/Prettier config for JS (none needed — no bundled JS pipeline).
- **Testing**: PHPUnit 11 configured ([phpunit.xml](phpunit.xml)), but only the two Laravel-default placeholder tests exist — **no real test coverage for any domain, including Brand**. User has flagged writing tests as future work.
